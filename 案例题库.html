核心心法：根因说"缺什么"，方案就"补什么"；一条根因配一条措施，编号对齐。症状≠根因，方案必须写，颗粒度要到具体技术。

万能三步 + 五大题型 必背

案例方法论 · 每题都按这个骨架答

它在讲怎么答题：案例题不是考背诵，是考能不能把考点落到具体场景。先定性 → 再给方案 → 最后论证。
万能三步：
① 定性：这是关于【XX】的问题（一句话点明考点）
② 定量/设计：方案 = 原理 + 场景适配 + 具体手段（写 3-5 个采分点）
③ 论证：因为【理由】，所以该方案能解决【原问题】
题型特征应对策略
概念辨析"什么是XX？XX和XX的区别？"先给定义 → 再列对比维度（表格/分点）
方案设计"请设计XX方案"场景分析 → 选型理由 → 具体设计（拓扑/流程）
问题定位"系统出现XX问题，原因可能有哪些？"从架构层/数据层/并发层/配置层逐层排查，每层 2-3 点
方案评价"该方案有哪些优缺点？"优点 + 缺点 + 改进建议，各 3 点
计算题可靠性/吞吐量/容量套公式，写清代入过程，单位别漏
💡 答题纪律：分点作答 (1)(2)(3)；先易后难；宁多勿漏（漏项不扣分）；答案里出现题干场景词，避免空话。

根因-方案一一对应（重点） 反复练

案例方法论 · 8/18、8/20、8/22、8/27 连续踩坑点

它在讲答题口径：故障排查题最怕"根因说缺××，方案却补了另一个××"。必须做到一条根因配一条措施，编号对齐。
⚠️ 症状 ≠ 根因：响应慢/超时/报错/丢消息是症状；根因 = 缺了哪个能力。
❌ 根因写"性能不足" → 太泛，等于没答
✅ 根因写"缺流量控制与削峰能力" → 标准口径
场景症状根因口径（缺××能力）方案（补××）
高并发请求超时/堆积缺流量控制与削峰能力限流 + 熔断 + 降级 + MQ 削峰 + 弹性扩容
连接池连接耗尽缺连接资源管控连接池调优 + 连接监控回收 + 读写分离/分库
重复消息重复发货/重复通知缺幂等性设计幂等表/唯一索引/状态判断去重
消息丢失部分订单状态不更新缺可靠投递与消费确认acks=all + ISR + 手动提交 offset + 幂等
超卖扣减量大于库存缺原子扣减与可靠锁Lua 原子扣减 + 分布式锁加固 + DB 条件更新兜底
雪崩依赖故障拖垮主链路缺故障隔离与兜底熔断 + 降级 + 限流 + 优雅下线
缓存穿透DB 压力大缺无效请求拦截布隆过滤器 / 空值缓存
缓存雪崩Redis 宕机后 DB 被打爆缺高可用与失效保护随机 TTL + 多级缓存 + 哨兵/集群 + 限流降级
✅ 口诀：根因说"缺什么"，方案就"补什么"；编号对齐，一条对一条。

高频案例考点清单 考前必扫

高频案例考点 · 与知识地图章节对应

  • 微服务拆分边界：按业务/领域拆，高内聚低耦合；网关 vs ESB；注册中心选型（Nacos/Eureka/ZK）
  • 分布式事务选型：强一致 → 2PC/TCC（钱/库存）；最终一致 → MQ/Saga（状态/通知）
  • 分布式缓存：穿透/击穿/雪崩三兄弟 + Cache Aside 一致性 + 分布式锁
  • 消息队列：Kafka 不丢/不乱/不重、消费积压、重平衡、死信队列
  • 分库分表：垂直/水平、路由规则、扩容平滑
  • 安全方案：等保2.0 测评流程、纵深防御、JWT vs Session
  • 高可用：双活/多活、故障转移、RPO/RTO 取舍
  • 质量属性权衡：性能 vs 安全、一致性 vs 可用性（必考权衡点）
  • 服务治理：熔断/限流/降级/灰度，雪崩三件套
  • 可观测性：日志/指标/链路追踪（SkyWalking 类）
💡 综合知识点学完后，案例直接套这份清单：学到一个考点，先问"它会不会变成案例场景？"会，就顺手练 1 道。

案例1：电商大促（订单超时/连接池/重复发货） 已练 8/20

经典案例 · 高并发 + 连接池 + 幂等三合一

📄 题目

电商大促期间出现三个问题：① 订单服务响应从 200ms 恶化到 5s，大量请求排队超时；② 数据库连接池"耗尽"告警；③ 支付回调重复到达导致部分订单重复发货。

请分别指出根因，并给出对应解决方案。

✅ 采分点
  • 根因①：缺流量控制与削峰能力 → 限流 + 熔断 + 降级 + Kafka 异步削峰 + 水平扩容 + 缓存
  • 根因②：数据库连接资源管控缺失（连接池配置不合理/连接长期占用不释放）→ 连接池调优 + 监控回收 + 读写分离/分库 + 热点缓存
  • 根因③：缺少幂等性设计（回调重复投递无去重）→ 支付流水号/订单号唯一标识幂等（幂等表/Redis SETNX）+ 执行前校验订单状态
📝 示范答案
  • ① 根因：缺流量控制与削峰能力（大促突发高并发，处理能力达瓶颈，请求堆积排队）→ 方案：限流+熔断+降级，Kafka 异步削峰，水平扩容+缓存
  • ② 根因：数据库连接资源管控缺失（连接池配置不合理，连接长期占用不及时释放）→ 方案：按物理资源调优连接池+监控连接及时回收，拆分数据库/读写分离，热点缓存 Redis
  • ③ 根因：缺少幂等性设计（回调重复投递无去重）→ 方案：支付流水号/订单号唯一标识幂等（幂等表/Redis SETNX），执行业务前校验订单状态

案例2：大促系统故障排查（Kafka丢消息/超卖/缓存雪崩） 已练 8/27 · 待重练

经典案例 · 中间件三连：消息可靠性 + 分布式锁 + 缓存雪崩

📄 题目

某电商平台采用微服务架构，订单服务与库存服务通过消息队列异步通信，库存扣减使用 Redis 分布式锁，商品详情使用 Redis 缓存。大促期间出现三个问题：

  • ① 用户支付成功后订单状态长时间不更新，部分订单支付成功但未发货；运维发现消息消费者频繁重平衡，消费者实例重启后存在消息丢失。
  • ② 秒杀商品库存扣减出现超卖，实际扣减量大于库存总量。
  • ③ 大促开始时大量商品详情请求响应超时，数据库压力飙升，同时部分 Redis 节点宕机。

请分别指出根因，并给出对应解决方案（根因与方案一一对应）。

✅ 采分点
  • ① 根因 2 分 + 方案 2 分：自动提交 offset（业务未完成即提交，崩溃丢消息）；消费能力不足 → 心跳超时 → 频繁重平衡
  • ② 根因 2 分 + 方案 2 分：扣减库存非原子 + 分布式锁不可靠（锁过期/主从丢锁）
  • ③ 根因 2 分 + 方案 2 分：缓存雪崩 = 大量 key 集中过期 + Redis 无高可用切换
📝 示范答案
  • ① 根因：消费者自动提交 offset，业务未完成就提交，宕机/重平衡后消息丢失；消费处理慢导致心跳超时频繁重平衡。方案：关闭自动提交、业务成功后手动提交 offset；优化消费逻辑、增加分区和消费者数（并行度=分区数），调大心跳超时/max.poll.records 避免重平衡；生产端 acks=all + min.insync.replicas 兜底。
  • ② 根因：扣减库存非原子操作 + 分布式锁不可靠（过期/主从丢锁），多个请求同时通过校验。方案：Redis Lua 脚本原子扣减（校验+扣减一步完成）；分布式锁加随机值+Lua 释放+看门狗续期；数据库兜底 UPDATE stock=stock-1 WHERE stock>0（条件更新/乐观锁）。
  • ③ 根因：大量 key 同时过期 + Redis 节点宕机无自动切换 → 请求穿透到 MySQL。方案：随机 TTL 避免集中过期；热点 key 永不过期+预热；Redis 主从+哨兵/集群高可用；兜底限流降级+多级缓存。
⚠️ 8/27 实战教训：① 方案必须写（只写根因 = 答一半）；② 超卖 ≠ 缺分布式事务，是"非原子扣减 + 锁不可靠"；③ 宕机+集中过期 = 雪崩，预热是措施、限流是兜底，都不能当根因。

案例3：银行核心交易系统（转账超时/连接池告警） 已练 8/18

经典案例 · 高并发性能 → 可用性

📄 题目

银行核心交易系统在高峰期转账请求大量超时，数据库连接池持续告警；直接扩容成本高，部分请求被丢弃。请分析根因并给出解决方案。

✅ 采分点
  • 根因：缺流量控制与削峰能力（高峰突发流量超过处理能力）→ 限流 + Kafka 削峰 + K8s 弹性扩容 + Redis 缓存热点
  • 根因：数据库连接池配置不合理/连接长期占用不释放 → 连接池调优 + 监控回收 + 读写分离/分库
  • 加分点：降级保护非核心功能、快速失败兜底、论证颗粒度到具体技术
📝 示范答案
  • ① 根因：缺流量控制与削峰能力（高峰流量超过系统处理能力，请求堆积）→ 方案：限流（令牌桶/漏桶）+ Kafka 异步削峰 + 水平扩容（K8s 弹性）+ 热点数据缓存 Redis
  • ② 根因：数据库连接资源管控缺失（连接池参数不合理、连接长期占用不释放）→ 方案：连接池参数调优（最大连接数/超时/回收）+ 连接监控告警 + 读写分离/分库
  • ③ 加分：降级非核心功能保核心转账链路，快速失败+兜底提示，避免请求无限堆积

案例4：直播大课（流量冲击/线程池打满/通知重复） 已练 8/21

经典案例 · 流量控制 + 异步兜底 + 幂等

📄 题目

在线教育平台直播大课开播瞬间大量用户涌入：① 核心接口响应急剧变慢；② 异步通知线程池被打满，部分任务延迟甚至丢失；③ 用户重复收到同一条通知。请分析根因并给出解决方案。

✅ 采分点
  • 根因①：缺流量控制能力 → 限流 + 熔断 + 降级 + 削峰
  • 根因②：线程池配置不足 + 任务无落库兜底 → 线程池调优 + 先持久化再异步 + 监控告警
  • 根因③：缺幂等性设计 → 通知唯一标识 + 幂等表去重
📝 示范答案
  • ① 根因：缺流量控制与削峰能力（开播瞬间突发流量超过处理能力）→ 方案：入口限流 + 依赖熔断 + 非核心降级 + MQ 异步削峰
  • ② 根因：异步处理线程池配置不足、任务未落库（内存中丢失）→ 方案：线程池参数调优（核心/最大/队列）+ 任务先落库/写 MQ 再异步消费 + 消费失败重试 + 监控告警
  • ③ 根因：缺少幂等性设计（重复投递无去重）→ 方案：通知内容生成唯一 ID，消费端幂等表/Redis SETNX 去重，业务前校验状态

案例5：微服务雪崩（依赖故障/请求堆积） 已练 8/22

经典案例 · 服务治理三件套 + 优雅下线

📄 题目

微服务 A 调用下游服务 B，B 出现故障后响应变慢，A 的线程资源被大量占用并快速耗尽，最终 A 也无法响应，故障向上游扩散。请分析根因并给出解决方案。

✅ 采分点
  • 根因：缺故障隔离与兜底（无熔断/降级/限流）→ 熔断（关闭→打开→半开）+ 降级（返回兜底）+ 限流（保护自身）
  • 加分点：服务优雅下线三步（注销注册 → 排空存量请求 → 停止实例）
📝 示范答案
  • ① 根因：缺故障隔离与兜底能力（B 故障后 A 无熔断保护，线程被慢调用占满，故障向上游扩散）→ 方案：熔断（状态机 关闭→打开→半开，试探恢复）+ 降级（B 不可用时返回兜底数据/快速失败）+ 限流（保护 A 自身资源）
  • ② 加分：发布/下线时执行优雅下线三步——先注销注册中心、再排空存量请求、最后停止实例，避免下线瞬间请求打到已停实例
  • ③ 论证：因为依赖故障被隔离在 B 周边，所以 A 的线程资源不再被慢调用耗尽，雪崩链路被切断
