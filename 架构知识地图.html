架构风格 已掌握

第7章 · 环节③"定骨架" · 综合单选必考

它在讲谁的什么：主语是整个系统的骨架——描述"系统分成哪些大块、块和块之间怎么通信"的宏观分类。一共就 4 类，看通信方式就能认出来。
4大类怎么通信代表判别词
调用/返回直接调用（打电话）主程序-子程序 / 层次 / 面向对象直接调用 / 调用清晰 / 分层
数据流数据流过（流水线）管道-过滤器流水线 / 加工 / 数据变换
独立构件发消息/事件（广播）事件驱动 / 发布-订阅发布/订阅 + 异步 + 消息队列 ⚠️
虚拟机引擎执行（读指令）解释器 / 规则系统读指令执行 / 规则 / 解释
⚠️ 3 大陷阱：
① 事件驱动 ≠ 显式调用 —— 事件驱动属于独立构件大类，发布者订阅者互不认识（必考易错点，钉死！）
② 层次结构只能调相邻层
③ 解释器 ≠ 管道-过滤器 —— 解释器"读指令执行"，管道过滤器"数据流过加工"
💡 事件驱动识别：服务 + 消息队列 + 异步解耦 + 发布/订阅 = 事件驱动

补充：真题常考风格（易漏）

  • 仓库风格（Repository）：中央数据仓库 + 一组独立组件；黑板是仓库的子类（数据驱动型）；传统数据库=外部驱动型仓库
  • C2 风格：组件+连接件分层、事件驱动；组件只与上下层连接件通信，组件之间不直接互调
  • 管道-过滤器：既是架构风格也是架构模式（数据流风格的具体实现）
⚠️ 辨析：发布订阅 ≠ 消息队列——发布订阅是通信模式（事件驱动风格），消息队列是实现载体；Kafka 用 MQ 实现发布订阅

架构模式 新学

第7章 · 环节④"做局部" · 判别看"协作方式"

它在讲谁的什么：主语是系统里的某个局部问题——"这一小块怎么搭"的现成套路，拿来就能用。今天背 4 个，看协作方式认。
① 分层 Layered 食堂打饭 · 各层只跟上下层打交道
  • 小白：点餐台 → 收银 → 后厨 → 仓库，各层只跟上下层打交道，不越级
  • 例子：银行核心系统（界面层-业务逻辑层-数据访问层-数据库）；TCP/IP 四层
  • 锚点："上下依赖、只调相邻层"
  • 易错：分层模式 ≈ 架构风格里的"层次结构风格"，一家人，别当两个东西；跨层调用=坏味道
② 代理 Proxy / Broker 买房中介 · 中间人转发，位置透明
  • 小白：买二手房找中介——你只跟中介打交道，不用知道房东是谁、在哪
  • 例子：远程调用（RMI / Web Service）；微服务网关转发
  • 锚点："中间人转发 + 位置透明"
  • 易错：代理是"帮你找到干活的人"，不是"替你干活"；客户端无感知
③ 黑板 Blackboard 专家围大白板 · 共享数据区协作
  • 小白：几个专家围一块大白板，谁有想法就写上，别人看到接着补充，轮流修正直到解出答案
  • 例子：语音识别（声学专家/语言专家轮流修正）；专家系统
  • 锚点："共享数据区 + 多个独立专家 + 协作求解"
  • 易错：黑板 ≠ 事件驱动！事件驱动是"喊话通知"，黑板是"共写一个本子"，不互相喊话
④ 模型-视图-控制器 MVC 餐厅 · 数据/展示/控制三分离
  • 小白：菜单只管展示（视图）、后厨只管做菜（模型）、服务员接单传话（控制器）
  • 例子：Spring MVC；前端框架
  • 锚点："数据-展示-控制三分离"
  • 易错：MVC 是表现层内部的分工，不是整个系统的架构风格；常作为分层结构中表现层的实现
✅ 判别总表（背这个）：分层 = 上下依赖 ｜ 代理 = 中间人转发 ｜ 黑板 = 共享数据协作 ｜ MVC = 展示与控制解耦

教材还提"客户机-服务器"模式：客户端发请求、服务器提供服务（B/S、C/S 就是它）。

💡 补充：MVVM = 模型-视图-视图模型（表现层模式，ViewModel 双向绑定）；中介者/观察者 = 面向对象架构模式（观察者是事件驱动思想的核心，发布订阅的本质）

重点：架构风格 vs 架构模式 重点

两者最易混淆 · 真题爱考"整体还是局部"

一句话分清：风格管整个系统的骨架（怎么通信），模式管局部怎么搭（怎么解决）。风格定骨架，模式定局部。
维度架构风格架构模式
管的是整个系统的骨架系统里某个局部的问题
回答的问题组件之间怎么通信这个具体问题怎么解决
抽象度高（抽象分类）低（具体套路）
数量只有 4 大类很多个
💡 对应关系（得分锚点）：调用/返回风格 → 分层模式；事件驱动（独立构件）风格 → 发布/订阅；数据流风格 → 管道-过滤器
⚠️ 真题怎么考：看到"整体 / 全局 / 组件间通信方式" → 风格；看到"局部 / 特定问题 / 可复用方案" → 模式。

4+1 视图模型 新学

第7章 · 环节⑤"画图纸" · 论文和综合都考

它在讲谁的什么：主语是系统的设计图纸——一套系统画 5 张图，每张给不同的人看：功能图、代码图、并发图、部署图、场景图（最重要）。
视图给谁看关心什么判别词
逻辑视图最终用户功能分解（类/对象/模块）功能 / 业务模块 / 用例
开发视图程序员代码模块/包结构代码 / 工程 / 包 / 层次结构
进程视图集成人员并发/同步/性能并发 / 同步 / 进程线程 / 性能 ⚠️
物理视图部署工程师硬件/服务器/网络拓扑服务器 / 机房 / 部署 / 网络
场景视图所有人典型用例串联验证，最重要场景 / 用例 / 驱动其他视图 ⚠️
⚠️ 3 个易错点：
① 进程视图 ≠ 业务流程图！并发/同步/性能才是进程视图；业务流程图属于逻辑视图
② 逻辑 vs 开发：逻辑 = 概念上的功能划分（不管代码怎么组织），开发 = 实际代码模块
③ 场景视图最重要 —— 考题爱考"哪个视图驱动其他视图"，答案永远是场景
✅ 得分锚点（论文直接用）："采用4+1视图描述架构：逻辑视图划分功能模块，开发视图组织代码结构，进程视图设计并发与通信，物理视图规划部署拓扑，场景视图以核心用例验证整体。"
综合题："并发 / 同步 / 性能" → 进程视图，闭眼选。

ABSD 方法（基于架构的软件开发） 新学

第7章 · 必考 · 综合单选

它在讲谁的什么：主语是开发流程——"先定系统要有多好（质量属性），再倒推架构怎么做"的开发方法，质量属性是贯穿全程的指挥棒。
  • 小白：别人先想功能再搭架子；ABSD 反过来——先定"要有多好"，再决定怎么盖
  • 流程：质量属性目标 → 质量场景说具体 → 选风格/战术 → 设计 → 实现 → 验证目标达成
  • 易错：核心驱动是质量属性不是功能需求；别和瀑布/敏捷混（那是按过程模型分，ABSD 按驱动因素分）
  • 锚点：问"ABSD 以什么为核心"→ 质量属性；问"输入"→ 质量场景
  • ABSD 四大输入（选择题）：功能需求 + 质量属性需求 + 业务环境 + 技术环境（"不属于输入的是哪个"是常考干扰项）

ADL（架构描述语言） 新学

第7章 · 必考 · 综合单选

它在讲谁的什么：主语是架构的表达方式——描述软件架构的专用语言，让计算机能读、能分析、能验证。
  • 三要素（必背）：组件 Component + 连接件 Connector + 架构配置 Configuration（谁、怎么连、怎么组装）
  • 易错：ADL ≠ UML——UML 通用建模偏描述，ADL 专用且支持形式化分析与验证
  • 补充：ADL 不包含用户界面描述（真题干扰项）；侧重静态架构，部分支持动态行为描述
  • 代表：AADL / Wright / Acme / Rapide
  • 锚点：看到"组件、连接件、配置"→ ADL；看到"形式化分析/验证架构"→ ADL

中间件技术 新学

第7章 · 必考 · 综合单选

它在讲谁的什么：主语是系统里的一层"翻译官"——位于操作系统与应用程序之间，屏蔽底层异构，向上提供统一接口（插座转换头）。
类别作用代表
消息中间件异步通信、解耦削峰Kafka / RabbitMQ
事务中间件管理分布式事务Tuxedo
对象中间件远程对象调用CORBA / RMI
应用服务器运行容器环境Tomcat / JBoss
数据库中间件统一数据访问/分库分表JDBC / MyCat
⚠️ 易错：中间件作用是屏蔽异构/解耦/复用，不是"让程序跑更快"；位置 = 操作系统之上、应用之下
💡 代表配对闭眼背：消息→Kafka、事务→Tuxedo、对象→CORBA/RMI、容器→Tomcat
💡 补充：RPC 中间件（Dubbo）——远程过程调用，核心三件：序列化 / 注册中心 / 负载均衡

微服务架构 新学

第7章 · 必考 · 综合+案例+论文三科全考

它在讲谁的什么：主语是系统的拆分与组织方式——把大系统拆成独立小服务，各自部署、通过接口通信（大食堂拆成独立小餐馆，一家爆满不影响其他家）。
4件套解决什么怎么做代表
拆分原则怎么拆按业务/领域边界拆，高内聚低耦合、独立部署独立库；不是越细越好DDD领域驱动
注册中心服务怎么找到彼此服务启动注册（IP+端口），调用方发现；本地缓存+心跳续约容错Nacos/Eureka/Consul/ZK
API网关统一入口路由转发/鉴权/限流/日志/灰度，管"外部→内部"Gateway/Kong
配置中心配置怎么管集中管理、动态下发、热更新，敏感配置加密Nacos/Apollo
⚠️ 易错：网关 vs ESB——网关管"外部→内部"统一入口；ESB（企业服务总线）管 SOA 时代"内部↔内部"集成（协议转换/路由），微服务时代被网关+服务治理取代（7/6错题）
💡 锚点：拆分看业务边界｜互相找靠注册中心｜统一进靠网关｜配置管理靠配置中心
💡 补充：服务发现两种模式——客户端发现（消费者自己查注册中心，Nacos/Eureka）/ 服务端发现（网关/负载均衡代理查询，K8s 模式）
SOA vs 微服务：SOA=重 ESB 总线、粗粒度服务、企业内部大系统改造；微服务=轻网关无 ESB、细粒度、去中心化（案例/论文高频）

服务治理：熔断/限流/降级/灰度 新学

第7章 · 必考 · 综合+案例

它在讲谁的什么：主语是微服务间的"交通治理"——服务多了像城市路口，靠四件套保证不堵死不瘫痪：熔断=断路保护、限流=限行、降级=高峰期停次要保核心、灰度=新版本小范围试通行。
机制干什么关键点代表
熔断下游故障时直接快速失败，防雪崩状态机：关闭→打开→半开（放少量请求试探）Hystrix/Sentinel
限流控制单位时间请求量令牌桶允许突发 vs 漏桶匀速平滑Sentinel/Guava
降级主动牺牲次要功能保核心链路被动保护=熔断；主动策略=降级开关/配置
灰度发布新版本先小范围试再全量先小后大+可回滚；≠滚动发布(一批批替换)网关权重/金丝雀
💡 锚点：雪崩→熔断降级｜高峰流量→限流削峰｜发新版→灰度。限流=挡，削峰=削，熔断=断
💡 补充：限流算法——计数器（固定窗口有临界突变漏洞，滑动窗口解决）/ 令牌桶（允许突发）/ 漏桶（匀速）；熔断半开：试探请求若再失败立即回到打开状态；蓝绿发布=两套完整环境瞬时切换（无流量损失、资源翻倍），与滚动（逐批替换）、灰度（小流量试）三兄弟对比

质量属性 已掌握

第8章 · 环节①"要什么" · 综合单选必考

它在讲谁的什么：主语是软件系统——功能回答"能干什么"（登录、转账），质量属性回答"干得好不好"（快不快、稳不稳、安不安全、好不好改、好不好用、好不好测）。考试考的就是这 6 个"干得好不好"的指标。
指标一句话判别词（看到就选它）
性能响应快、吞吐高延迟 / 吞吐量 / 并发量 / 1秒内响应
可用性不出错、故障能恢复7x24 / 冗余 / 容错 / 故障转移 / 心跳
安全性防攻击、权限、加密认证 / 授权 / 加密 / 防火墙 / 防篡改
可修改性好改、好扩展加功能容易 / 模块化 / 低耦合 / 热插拔
易用性好用、好上手提示清晰 / 操作友好 / 用户可恢复 ⚠️
可测试性方便测试、能验证测试用例 / 可观测 / 可诊断 / 覆盖率
⚠️ 易用性 vs 可用性："输入非法数据有清晰提示"是易用性（用户友好），不是可用性（系统不宕机）。
✅ 教材第2版六大质量属性：性能 / 可用性 / 安全性 / 可修改性 / 可测试性 / 易用性。
· 互操作性、可移植性等属于 SEI 体系扩展属性，真题问"是否属于质量属性"时它们也算；但问"教材六大"，答案用带"可测试性"的版本。
· 也别和 ISO 质量模型（9126/25010）混淆：功能性 / 可靠性 / 易用性 / 效率 / 维护性 / 可移植性。

质量属性战术（🔴 ATAM 案例必考）

属性战术（考试按属性背）
可用性故障检测（心跳/异常检测）→ 故障恢复（冗余/重定向/故障转移）→ 故障预防（主动监控）
性能资源需求管理（并发/队列）→ 资源管理（调度/多线程）→ 资源仲裁
安全性攻击检测 → 攻击抵抗（认证/授权/加密）→ 反应与恢复
可修改性局部化修改 → 防止连锁反应（解耦）→ 延迟绑定时间
💡 答题：ATAM 案例问"采用什么战术满足 XX 质量属性"→ 按上表对号（如"心跳检测"=可用性故障检测战术）

质量场景 已掌握

第8章 · 环节②"说清楚" · 六要素必考

它在讲谁的什么：主语是质量属性——它是把"系统要有多好"说具体的填空模板。光说"系统要可用"太笼统，用 6 个空填满：谁、在啥时候、对啥、做了啥、系统咋回应、算多好。
6要素含义举例（可用性）
刺激源谁发起的用户
刺激发生了什么发起转账请求
环境什么状态下发生的高峰期 ⚠️
工件作用于哪个系统银行核心系统
响应系统怎么回应1秒内返回成功
响应度量怎么算达标成功率 ≥ 99%
⚠️ 易错点："高峰期 / 故障中 / 正常运行" → 环境，不是响应！

CAP 定理 + BASE 理论 新学

必考 · 综合单选高频

它在讲谁的什么：主语是分布式系统的取舍规则——网络必然可能断（P必须保），所以一致性与可用性只能二选一；BASE 是选"可用性优先"后的落地理论。
概念含义典型
CP一致性优先，牺牲可用性（报错也不给错数据）银行转账 / 库存扣减
AP可用性优先，牺牲一致性（先响应，稍后同步）商品浏览 / 社交点赞
BASE基本可用 + 软状态 + 最终一致性（AP的落地版）分布式场景普遍
ACID强一致（单库事务），与 BASE 是两条路线关系型数据库事务
⚠️ 易错：CAP 不是"三选二随便挑"，是 P 必保、CA 二选一；BASE ≠ 放弃一致性，是"最终一致"；网络分区 ≠ 机器宕机（分区=节点间消息丢失延迟，宕机=节点本身挂了，选择题坑）
💡 锚点：钱/库存→CP强一致；浏览/点赞→AP最终一致

分布式事务 新学

必考 · 综合+案例

它在讲谁的什么：主语是跨服务/跨库操作的原子性——一个操作涉及多个服务（下单=订单+库存+积分），要保证全成功或全失败。
路线方案适用缺点
强一致2PC（准备→提交，协调者主导）金额、库存强扣减同步阻塞、协调者单点
强一致TCC（Try-Confirm-Cancel 手工补偿）可接受业务侵入代码复杂
最终一致MQ+本地消息表订单状态、通知类有短暂不一致窗口
最终一致Saga（长事务反向补偿）长链路业务补偿逻辑要写好
⚠️ 易错：Saga 是最终一致的补偿式长事务，不是两阶段提交；2PC 才是强一致。扣库存选强一致（防超卖），通知积分可最终一致
💡 选型口诀：钱和库存→2PC/TCC；状态和通知→MQ/Saga
💡 补充：3PC = 三阶段提交（CanCommit/PreCommit/DoCommit），引入超时解决 2PC 协调者单点阻塞，但极端情况仍可能不一致；Saga 两种模式——编排式（中央协调器指挥各服务）/ 协同式（服务间事件通知，无中央协调器，案例考过）

分布式缓存：穿透/击穿/雪崩/一致性 新学

第6章 · 必考 · 综合+案例高频

它在讲谁的什么：主语是数据库前面那层"快查柜台"——缓存用不好有四个坑：穿透/击穿/雪崩（三兄弟）+ 一致性（写库与写缓存的顺序）。
坑判别词首选解法
穿透查不存在的数据（假ID/恶意请求）布隆过滤器 / 空值缓存
击穿热点key过期瞬间大量请求涌入互斥锁重建 / 热点永不过期+预热
雪崩大量key同时过期（或节点宕机）随机TTL / 多级缓存 / Redis高可用 / 限流降级兜底
一致性更新DB后缓存是旧的Cache Aside：先写DB→再删缓存（下次读时重建）
⚠️ 易错：先删缓存再更新DB会有一致性窗口（读到旧值）；极端场景用延迟双删 / binlog订阅（Canal）
💡 Redis 高可用三件套：主从=读写分离 ｜ 哨兵=主挂自动切换 ｜ 集群=分片扩容。穿透→布隆过滤器（挡不存在）；击穿→锁+永不过期（护热点）

缓存更新策略全集（选择题干扰项高发）

策略谁负责查库/写库流程特点
Cache Aside（最常用）应用自己读：先查缓存→miss查库→回填；写：先更新库→再删缓存灵活，一致性较好
Read-Through 读穿透缓存组件缓存miss时由缓存组件查库并回填，应用不直接查库把"查库+回填"封装进缓存服务
Write-Through 写穿透缓存组件应用只写缓存，缓存同步写库一致性最好，每次写两次IO（慢）
Write-Back 回写缓存组件只写缓存立即返回，异步批量落库最快，但缓存挂可能丢数据

Redis 集群哈希槽：共 16384 个槽，key 按 CRC16(key)%16384 归属槽，槽分配给节点；节点增减只迁移部分槽（比一致性哈希更均匀可控）。

缓存预热：上线前把热点数据预先加载进缓存（开业前先备好货），避免上线瞬间大量 miss 打库；缓存降级：缓存故障/压力大时主动降级（直连库+限流兜底），保证核心可用。

消息队列 Kafka 完整考点 高频必考

第6章 · 选择题+案例+论文全覆盖

它在讲谁的什么：主语是系统间的消息通道——异步解耦削峰。完整考点：核心组件 / acks 配置 / 消费者语义 / 高吞吐原理 / 故障案例模板 / 高频坑点。

① 核心组件（🔴必背）

组件考试要点
BrokerKafka 服务实例，多台组集群；旧版 ZooKeeper 存元数据，新版 KRaft（Raft 协议）去 ZK
Partition 分区Topic 物理分片、分散多 Broker 水平扩展；分区内有序、跨分区无序；消费最大并行度=分区数；带 key→哈希固定分区，key=null→轮询；⚠️只能增加不能减少
Replica 副本每分区多副本分布不同 Broker；Leader 负责全部读写，Follower 只同步；Leader 挂→Follower 竞选
ISR同步副本集合（Leader+不落后的 Follower）；只有 ISR 内可竞选 Leader；落后被踢出、追上再加入；unclean.leader.election.enable=false 禁脏选举（防丢消息）
Offset分区内消息递增编号，存内置 topic __consumer_offsets；消费只移动 offset 不删消息，按保留时间清理，可重置回放（Kappa 核心）
Consumer GroupPull 拉模式；同一分区只给组内 1 个消费者，1 个消费者可消费多分区；消费者数>分区数→多出空闲
Rebalance组内增减消费者/心跳超时/分区变化触发；重平衡期间消费暂停，频繁触发性能恶化

② Producer 应答 acks（🔴必考）

acks含义可靠性
0发送完不等应答最低，可能丢（日志埋点）
1（默认）Leader 写入即返回中等，Leader 挂且 Follower 未同步会丢
all(-1)ISR 全部副本写完才成功最高（订单/支付核心业务）

配套参数：retries 重试（会产生重复消息）｜ min.insync.replicas ISR 最少存活数，不足直接拒写（宁可不可用不丢数据）｜ enable.idempotence 幂等生产者（只解决生产者重试重复，解决不了消费端重复）

③ 消费者考点（🔴）

  • 自动提交 enable-auto-commit：定时提交，业务没执行完 offset 已提交→崩溃丢消息（风险）
  • 手动提交：业务完成再提交；失败不提交→重启重读（重复消费风险，Kafka 默认 At-Least-Once）
  • auto-offset-reset：earliest=从最早开始；latest=只消费新消息
  • 投递语义三选一：At-Most-Once 至多一次（丢不重）｜ At-Least-Once 至少一次（默认，重不丢→业务必须幂等） ｜ Exactly-Once 精确一次（幂等生产者+Kafka事务，开销大）

④ 为什么吞吐极高（🟡论文可写）

  • 顺序追加写：Partition 只 append，磁盘顺序 IO 极快
  • PageCache：走操作系统页缓存，避开 JVM 堆、减 GC 压力
  • 零拷贝：sendfile 磁盘→网卡，减少内存拷贝
  • 批量发送 + 消息压缩

⑤ 故障大全（🔴案例头号考点）

故障根因解决
消息丢失acks=0/1；副本数=1；开启脏选举；消费端自动提交 offsetacks=all+重试；副本≥3；关 unclean 选举；min.insync.replicas；手动提交 offset
重复消费生产者重试；业务完成未提交 offset 就宕机业务幂等（幂等表/唯一索引/状态判断）
乱序全局无序相同业务 key → 同一分区
积压 lag消费逻辑慢；消费者数>分区数；业务阻塞优化逻辑；加消费者（≤分区数）；加分区

⑥ 高频坑点（极易选错）

⚠️ ① 消费≠删消息（只移 offset，消息按时间清理）② 消费者越多越快 ❌（并行度=分区数）③ Follower 不处理读写 ④ 幂等生产者≠解决消费端重复 ⑤ ISR 外副本默认不能选 Leader ⑥ Kafka 是 Pull 拉模式 ⑦ 分区只能增不能减 ⑧ acks=all 是等副本确认不是删消息

⑦ 中间件对比（选择题）

中间件特点适用
Kafka极高吞吐、持久化、可回放日志/大数据/Kappa/削峰解耦
RabbitMQAMQP、灵活路由业务异步、复杂路由
RocketMQ事务消息、顺序消息电商金融

MQ 四大作用（论文可写）：应用解耦 / 异步处理 / 流量削峰 / 分布式最终一致性

⑧ Kappa vs Lambda（🟡）

Lambda = 批处理层 + 流处理层两套代码；Kappa = 只用流处理引擎，历史数据通过重置 Kafka offset 回放重算，不需要独立批处理层。考题：Kappa 历史数据重处理 → 重置消费 offset。

⑨ 案例答题模板（直接抄）

① 消息丢失：根因=自动提交 offset 业务未完成即提交、崩溃丢失 → 解决=关闭自动提交、业务完成手动提交 offset
② Leader 宕机丢消息：根因=开启 unclean 脏选举、落后副本当 Leader → 解决=关闭脏选举 + acks=all + min.insync.replicas
③ 重复消费：根因=至少一次投递 + 未提交 offset 宕机 → 解决=业务幂等（幂等表/唯一索引）
④ 消费积压：根因=消费慢/消费者超分区数 → 解决=优化消费逻辑 + 加分区 + 对应数量消费者

死信队列 DLQ（案例故障高频）

  • 为什么需要：消息多次消费失败（业务异常/数据问题），无限重试=死循环+阻塞正常消息
  • 机制：消费失败 → 重试 N 次（退避）仍失败 → 投递到 DLQ（专门的死信 topic）
  • DLQ 消息怎么再次消费：① 修复后重放（人工/定时任务把 DLQ 消息重新投递回原队列；先修数据或代码）② 专门消费程序（另起消费者组消费 DLQ 做补偿/告警/人工介入）③ 管理工具手动 requeue
  • 类比：DLQ=问题件仓库——送不出去先放仓库，排查原因（改地址=修数据、换路线=修代码）后重新派送

Kafka 事务（Exactly-Once）

  • 幂等生产者（enable.idempotence）：每个 Producer 有 PID，消息带序号，Broker 按 PID+序号去重 → 解决"生产者重试产生的重复"
  • 事务（transactional.id）：把"消费+处理+再生产+提交offset"纳入一个事务，全成或全败 → 解决跨 topic 链路的原子性
  • epoch：事务代数——生产者重启 epoch+1，Broker 拒绝旧 epoch 请求，防"僵尸生产者"写脏数据
  • 代价：性能开销大；幂等生产者≠端到端 Exactly-Once，需配合事务

Rebalance 重平衡（触发条件完整版）

  • ① 消费组增/减消费者（新加入要分分区；退出/宕机要重新分配）② 心跳超时（与协调者失联视为死亡）③ 分区数量变化（Topic 加分区）④ 订阅 topic 变化（正则订阅匹配到新 topic）
  • 重平衡期间消费暂停，频繁触发=性能恶化；类比：有人加入/离开或活变多，都要"开会重新分活"，开会期间停工

分布式锁 新学

第6章 · 必考 · 综合+案例（抢购扣库存场景）

它在讲谁的什么：主语是跨机器的锁——多台服务器同时改同一资源（抢购扣库存），单机锁管不住别的机器，需要一把跨机器都能认的锁。
坑问题解法
① 死锁拿锁后崩溃，锁永不释放EX 过期时间，到期自动释放
② 误删A 的锁过期后 B 加锁，A 却删了 B 的锁value 用唯一随机值，删除前校验是自己的，校验+删除用 Lua 原子执行
③ 锁过期业务没干完锁就过期，别人也进来看门狗（Redisson）自动续期
④ 主从丢锁Redis 主挂了，锁没复制到从节点RedLock 红锁（多节点多数派）/ Zookeeper 临时顺序节点
⚠️ 易错：本地锁（synchronized）只管单机，分布式锁管多机；锁必须有过期时间
💡 答题链路：SETNX 拿锁 → EX 防死锁 → 随机值防误删 → 看门狗续期 → 极端场景 RedLock/ZK
💡 补充：Zookeeper 锁 = 临时顺序节点（会话结束自动删除→天然防死锁），强一致但性能低；对比——Redis 锁高性能需处理过期/误删/主从丢锁，ZK 锁强一致性能低：高并发选 Redis，强一致选 ZK
